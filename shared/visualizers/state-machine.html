Game States: One Game, Several Modes

Why the same key does different things at different times. Used in: web L5 · python L6 · c++ L6

A game is never doing just one thing. Sometimes it is showing a menu. Sometimes it is playing. Sometimes it is paused. The trick is that it is only ever in exactly one of these at a time, and that single fact removes an enormous amount of confusing code.

What to look for Press the buttons in any order you like. Two things to notice. First, the same button does different things depending on the glowing box. Second, most presses are ignored — try pressing P to pause while you are on the menu. Nothing happens, and that is correct behaviour, not a missing feature.

What this replaces

Without states — the tangle

// flags everywhere
let started = false;
let paused = false;
let dead = false;
let inMenu = true;

if (started && !paused && !dead) {
  updatePlayer();
}
if (!started && inMenu && !dead) {
  drawMenu();
}
// ...and what does it mean
// if started AND inMenu are
// both true? Nobody knows.

With one state — the untangle

// ONE variable. One truth.
let state = "MENU";

function update(dt) {
  if (state === "PLAYING") {
    updatePlayer(dt);
    updateEnemies(dt);
  }
  // PAUSED updates nothing,
  // which is the whole point
  // of being paused.
}

function draw() {
  if (state === "MENU")    drawMenu();
  if (state === "PLAYING") drawGame();
  if (state === "PAUSED")  { drawGame(); drawPauseOverlay(); }
  if (state === "GAME_OVER") drawScores();
}
The big idea: make illegal situations impossible

With four separate true/false flags there are 2×2×2×2 = 16 combinations, and only four of them make any sense. The other twelve are bugs waiting to happen — paused and dead and in the menu at once.

With one state variable there are exactly four possibilities, and all four are valid. You did not fix those twelve bugs. You made them impossible to write. That is a much stronger kind of fix, and looking for chances to do it is one of the most valuable habits in all of programming.

A common mistake

Students often put the pause check inside every single object:

// in the player, and the enemy, and the bullet, and the particles...
if (!paused) { this.x += this.vx * dt; }

Now pausing depends on remembering that check in twenty places, and you will forget one — so one enemy keeps walking while the game is paused. Check the state once, in the loop, and simply do not call update at all.

Think like an engineer

Draw the state diagram for a game you actually play. Include the states most people forget: the loading screen, the settings menu, the cutscene, the “are you sure you want to quit?” box, the level-complete screen.

Then find a transition that should not be allowed and ask what would go wrong if it were. For example: what breaks if you could go from PAUSED straight to GAME_OVER? Finally, think about where the music should change — is music a part of the state, or a reaction to it?

Vocabulary
  • State machine — a design where a thing is in exactly one named state at a time, and only certain moves between states are allowed.
  • State — one of the named modes. (Careful: this word also means “all the numbers the game remembers”. Both uses are standard, and you work out which from context.)
  • Transition — a permitted move from one state to another.
  • Event — something that happens, such as a key press, that may cause a transition.
